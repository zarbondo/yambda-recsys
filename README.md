# Рекомендации музыки на Yambda

Двухэтапная рекомендательная система на открытом датасете Яндекс Музыки
[Yambda](https://huggingface.co/datasets/yandex/yambda), версия 50M:
10 000 юзеров, ~934 тыс. треков, 46 млн прослушиваний и 880 тыс. лайков.

Задача — по истории прослушиваний и лайков подобрать юзеру **новые** треки, которые он
дослушает или лайкнет на следующий день. Уже знакомые треки из рекомендаций выкидываем:
в музыке много повторных прослушиваний, и угадать, что человек снова включит любимую
песню, несложно, а интересно именно найти новое.

## Как устроено

**1. Кандидаты** (до ~230 на юзера, с пересечениями меньше):

- **ALS** (implicit) по матрице юзер × трек, вес = log(1 + число listen+) + бонус за лайк;
- **item2item по переходам**: какие треки слушают сразу после трека в той же сессии.
  Берём последние 20 треков юзера, свежие весят больше, и собираем их соседей;
- **популярное** за последние 7 дней.

**2. Ранжирование**: CatBoost с лоссом YetiRank, группа = юзер. Фичи:

- скоры и ранги из генераторов, сколько генераторов предложили трек;
- скор ALS для всех кандидатов, а не только для тех, что принёс ALS;
- трек: популярность за всё время, 7 дней и последний день, тренд, skip rate, доля лайков,
  доля органики, длина, «возраст» в данных;
- юзер: активность, доля дослушанного, доля органики, сколько дней молчал;
- юзер × артист: какая доля прослушиваний юзера приходится на артиста трека.

Позитив — listen+ (дослушал хотя бы половину трека, как в протоколе Yambda) или лайк.

## Сплит без утечки

Глобальный временной сплит по протоколу из [статьи Yambda](https://arxiv.org/abs/2505.22238):
последний день — тест, между историей и тестом 30 минут зазора, юзеров без истории
не оцениваем. Ранкер учится на дне перед тестом, и генераторы для него видят только то,
что было до этого дня. Перед тестом все генераторы переобучаются на свежей истории.

```
фаза A:  история ──────────────┤ 30м │ день ранкера (таргеты A) │
фаза B:  история ───────────────────────────────────────────────┤ 30м │ тест, 1 день (таргеты B) │
```

Все фичи считаются только по истории своей фазы, будущее в них не попадает
(в `slice_phase` на это стоит assert, есть тесты).

## Запуск

```bash
pip install -r requirements.txt

python main.py --smoke     # прогон на синтетике в схеме yambda, ~1 минута — проверить, что всё работает
python main.py             # полный прогон на Yambda-50M, данные скачаются с HuggingFace
python -m src.eda          # статистика и графики по датасету
pytest                     # тесты метрик и сплита

mlflow ui --backend-store-uri sqlite:///mlflow.db   # история экспериментов
```

Самая долгая часть — ALS на CPU. Если не хватает времени или памяти, уменьши
`candidates.als.iterations`, подними `candidates.als.min_item_count` или сократи
`candidates.i2i.days` в `configs/default.yaml`. CatBoost можно перевести на GPU
(`ranker.task_type: GPU`).

## Структура

- `configs/` — гиперпараметры (`default.yaml` — 50M, `smoke.yaml` — синтетика)
- `src/data/` — загрузка, временной сплит, генератор синтетики
- `src/candidates/` — ALS, item2item, популярное
- `src/ranking/` — фичи и CatBoost-ранкер
- `src/evaluation/` — NDCG@k, Recall@k
- `src/pipeline.py` — одна фаза: история → кандидаты → фичи
- `main.py` — обе фазы, обучение ранкера, оценка, логирование в MLflow
- `tests/` — тесты метрик и сплита
